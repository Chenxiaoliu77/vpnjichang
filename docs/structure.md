# 目录结构与文件组织

本文面向**仓库维护者**，说明 vpnjichang 的目录为什么这么切、每个文件负责什么、扩展时该往哪里加。

## 全貌

```
vpnjichang/
├── README.md                  # 项目说明 + 收录清单（清单区块由脚本渲染生成）
├── CHANGELOG.md               # 变更记录：每次增删改收录项都记一笔
├── CONTRIBUTING.md            # 贡献指南：如何新增 / 更新 / 下架一个收录项
├── LICENSE                    # MIT 许可证
├── .gitignore                 # 忽略 Node 依赖与本地临时文件
├── .github/
│   └── workflows/
│       ├── ci.yml             # CI：结构校验 + README 渲染一致性 + 链接巡检
│       └── link-check.yml     # 定期巡检：每周一三五，可手动触发
├── data/
│   ├── links.json             # ★ 收录清单唯一真源（结构化数据）
│   └── links.schema.json      # links.json 的 JSON Schema
├── docs/
│   ├── structure.md           # 本文件
│   └── link-formats.md        # 链接形式规范：深链 / 服务端推广码 / 渠道标记
└── scripts/
    ├── validate-links.mjs     # 零依赖校验器：结构、参数一致性、重复项
    ├── render-readme.mjs      # 由 links.json 渲染 README 的清单区块
    └── check-links.mjs        # 可达性巡检：区分真失效与风控拦截
```

## 核心设计：单一真源 + 渲染

### 数据流

```
data/links.json  ──┬──>  scripts/validate-links.mjs  ──>  结构/一致性校验（CI 步骤 1）
                    │
                    ├──>  scripts/render-readme.mjs  ──>  README.md 的清单区块（CI 步骤 2 校验一致性）
                    │
                    └──>  scripts/check-links.mjs  ─────>  探测各链接，写回 probe 字段
                                                              （CI 步骤 4 / 定期工作流）
```

**唯一真源是 `data/links.json`。** README 里由脚本托管的两块内容被成对的标记注释包住：

```
<!-- BEGIN:LINKS_TABLE (generated by scripts/render-readme.mjs; do not edit by hand) -->
<!-- END:LINKS_TABLE -->

<!-- BEGIN:LINKS_DETAILS (generated by scripts/render-readme.mjs; do not edit by hand) -->
<!-- END:LINKS_DETAILS -->
```

在这两块里手写内容会在下次渲染时被**静默覆盖**。CI 用 `node scripts/render-readme.mjs --check` 兜底：只要 README 与数据不一致，CI 立刻失败，不会让覆盖悄悄发生。

### 为什么不用 Markdown 当真源

如果清单直接写在 Markdown 里，就会出现两难：Markdown 好读但机器不好解析；JSON 好解析但人不好维护。折中方案是**JSON 存数据 + 脚本渲染 Markdown**，代价是多一个渲染步骤，收益是：

- 清单能被程序校验（重复 URL、推广码与链接形式不匹配、id 冲突……）；
- 字段的必填与类型由 schema 约束，新增条目不会漏字段；
- 改一次数据，README 的表格和正文同步更新，不会出现「表格里改了、正文里忘了改」。

## 各文件职责

| 文件 | 职责 | 谁来改 |
| --- | --- | --- |
| `data/links.json` | 收录清单唯一真源 | 任何人（新增/更新/下架条目） |
| `data/links.schema.json` | 清单的 JSON Schema，定义每个字段的类型与约束 | 字段语义变更时 |
| `README.md` | 面向访客的项目说明；清单区块由脚本托管 | 说明性文字可手改；清单区块勿手改 |
| `docs/structure.md` | 本文件：目录组织与设计决策 | 目录结构调整时 |
| `docs/link-formats.md` | 链接形式规范与参数填写规则 | 新增链接形式时 |
| `scripts/validate-links.mjs` | 零依赖结构与一致性校验器 | 校验规则变更时 |
| `scripts/render-readme.mjs` | 由数据渲染 README 清单区块 | 渲染样式变更时 |
| `scripts/check-links.mjs` | 可达性巡检器 | 判定规则变更时 |
| `.github/workflows/ci.yml` | 跑校验 + 一致性检查 + 巡检 | 流程调整时 |
| `.github/workflows/link-check.yml` | 定期巡检工作流 | 巡检频率调整时 |
| `CHANGELOG.md` | 变更记录 | 每次合并实质变更时 |
| `CONTRIBUTING.md` | 贡献指南 | 流程变更时 |

## data/links.json 字段详解

```
{
  "version": 1,
  "updatedAt": "2026-10-31",
  "maintainer": "Chenxiaoliu77",
  "links": [
    {
      "id": "chui-xue-yun",
      "name": "吹雪云",
      "nameZh": "吹雪云（Wind sweeps the cloud-snow）",
      "punycodeDomain": "xn--9kqs1lo79d.com",
      "unicodeDomain": "吹雪云.com",
      "category": "provider",
      "categoryLabel": "机场订阅服务商（注册深链）",
      "url": "https://xn--9kqs1lo79d.com/#@command:register?code=o31fm0TO",
      "urlKind": "hash-deep-link",
      "referralCode": "o31fm0TO",
      "cover": null,
      "purpose": "一句话说明这条地址干什么",
      "description": ["分段说明……", "……"],
      "tags": ["深链注册", "带推广码"],
      "pricing": [{ "plan": "Basis 基础套餐", "price": "¥9.9 / 月（500G）" }],
      "platforms": ["iOS", "Android", "Windows"],
      "protocols": ["Clash", "sing-box"],
      "backupUrls": ["https://example.com/backup"],
      "contact": ["https://t.me/example"],
      "verified": {
        "checkedAt": "2026-10-31",
        "httpStatus": 200,
        "finalUrl": "https://example.com/",
        "method": "curl + read_page",
        "note": "核验结论与未核验事项"
      }
    }
  ]
}
```

### 标识类

- **`id`** —— 条目唯一标识，小写字母/数字/连字符。它是变更追踪的锚点，**一旦发布就当作破坏性变更**：改名等于换一个条目。
- **`name` / `nameZh`** —— 对外展示名。`nameZh` 可以带上站点的自述标语（如「良心云 最良心的高性价比机场」），便于识别。

### 域名类

- **`punycodeDomain` / `unicodeDomain`** —— IDN 域名的两种写法。校验器强制两者不得相同（即不得有一方被写成另一方的复制），确保是真的做了 Punycode ↔ Unicode 对照，而不是把同一个字符串填两遍。

### 分类类

- **`category`** —— 机器可读枚举，取值：
  - `provider` —— 机场/代理订阅服务商；
  - `affiliate` —— 联盟推广后台（如 mitce 的 `affiliates.php`）；
  - `mirror` —— 镜像/备用入口；
  - `tool` —— 工具类；
  - `tutorial` —— 教程。
- **`categoryLabel`** —— 人类可读的中文标签，直接渲染进表格。

### 链接类

- **`url`** —— 完整地址，必须是 `https://`。
- **`urlKind`** —— 决定推广码该放在哪里，也是校验器判断一致性的依据：

  | 取值 | 含义 | 推广码位置 |
  | --- | --- | --- |
  | `hash-deep-link` | 客户端深链 | fragment：`#@command:<cmd>?code=...` |
  | `path-referral` | 服务端推广链接 | query：`?code=...&cover=...` |
  | `path-page` | 站内页面 | 无 |
  | `plain` | 普通链接 | 无 |

- **`referralCode`** —— 推广码。校验器强制：`hash-deep-link` 与 `path-referral` 必须有，`affiliate` 类必须没有。
- **`cover`** —— 渠道/落地页来源标记，**只允许出现在 `path-referral` 里**。

### 内容类

- **`purpose`** —— 一句话，回答「这条地址是干什么的」。
- **`description`** —— 分段说明数组。写清三件事：**站点性质**（是服务商还是联盟页）、**链接参数含义**、**注意事项**（如需浏览器打开、需登录）。
- **`tags`** —— 短标签，用于表格速览与检索。
- **`pricing`** —— 站点**公开公示**的套餐。只填页面上真实看到的，不填推测值。
- **`platforms` / `protocols`** —— 支持平台；客户端与协议标识。
- **`backupUrls` / `contact`** —— 备用入口（防失联发布页、备用域名）与客服/社群。

### 核验类

- **`verified.checkedAt`** —— 核验日期（`YYYY-MM-DD`）。
- **`verified.httpStatus`** —— 实测 HTTP 状态码。**403 是合法且常见的结果**，表示站点部署了 Cloudflare 人机校验。
- **`verified.finalUrl`** —— 跟随重定向后的最终地址。
- **`verified.method`** —— 核验方式，如 `curl + read_page`。
- **`verified.note`** —— 核验结论与**未核验事项**。这一条最要紧：写清「哪些信息没验证到」，避免读者把空白误读成「该特性不存在」。

### 巡检类（机器写入）

`probe` 字段由 `scripts/check-links.mjs --update` 写入，`verified` 则是人工核验记录。两者并存，含义不同：

| | `verified` | `probe` |
| --- | --- | --- |
| 写入者 | 人工（读页面内容） | 脚本（只发 HTTP 请求） |
| 能看出什么 | 站点性质、套餐、协议、需登录 | 仅可达性与最终地址 |
| 适合回答 | 「这家是干什么的、多少钱」 | 「链接还能不能打开」 |

## scripts/check-links.mjs —— 可达性巡检

这是本仓库的保鲜机制：机场域名变动频繁，靠人工复查必然烂尾。

### 核心判定原则

**HTTP 403/503/429 + Cloudflare 人机校验标记 = 站点活着，只是脚本过不去。**

把 403 当成失效，是这类巡检最容易犯的错误——本仓库 8 条里有 4 条会稳定返回 403，若按「非 200 即失效」判定，巡检第一天就是全红。

### health 字典

| health | 含义 | 致命 | 说明 |
| --- | --- | --- | --- |
| `ok` | 正常 | 否 | 2xx 响应 |
| `cloudflare` | 风控拦截 | 否 | 403/503/429 且响应体含 CF 校验标记 |
| `redirected` | 已跳转 | 否 | 3xx 未落到最终地址 |
| `blocked` | 疑似访问限制 | 否 | 401/403 且无 CF 标记 |
| `server-error` | 服务端错误 | 否 | 5xx |
| `notfound` | 页面不存在 | **是** | 404 / 410 / 451 |
| `timeout` | 请求超时 | **是** | 超时（默认 20s） |
| `unreachable` | 无法连接 | **是** | DNS 失败 / 连接被拒 / 证书错误 |

### 漂移分级

巡检结果**受出口 IP 影响**——同一站点在本地和 GitHub runner 上可能一个返回 200、另一个被 Cloudflare 拦截。因此漂移分四级，**只有 alert 级才判失败**：

| 级别 | 触发条件 | 处置 |
| --- | --- | --- |
| `alert` | 最终地址**域名变化**、或健康状态转为致命 | 判失败，需人工确认 |
| `warn` | 两个非致命状态之间变化（如 ok ↔ cloudflare） | 提示，不判失败 |
| `info` | 状态码变了但健康等级未变 | 忽略 |
| `notice` | 首次巡检，无基线 | 建立基线 |

**域名变化是唯一必须人工确认的信号**——机场换域名后，旧推广链接会直接失效，佣金也会断。

### 命令

```bash
node scripts/check-links.mjs                # 巡检并打印报告，不写文件
node scripts/check-links.mjs --update       # 巡检并把结果写回 data/links.json 的 probe 字段
node scripts/check-links.mjs --check        # 巡检并与已存 probe 比对，alert 级漂移判失败
node scripts/check-links.mjs --json         # 机器可读 JSON 输出
node scripts/check-links.mjs --out r.json   # 报告写入文件
node scripts/check-links.mjs --only mitce   # 只巡检指定条目
node scripts/check-links.mjs --timeout 30000 --concurrency 6 --retries 3
```

退出码：`0` 无失效无告警；`1` 有确认失效或 alert 级漂移；`2` 参数或文件错误。

### 用法要点

- **更新基线要在本地跑**，不要在 CI runner 上跑 `--update`。runner 出口 IP 与本地不同，自动写回会污染本地基线，下次本地巡检就会报一堆假漂移。
- 定期工作流 `link-check.yml` 只产出报告 artifact，不写回仓库；需要更新基线时在本地执行 `--update` 后再提交。
- 巡检只发 HTTP 请求，**不登录、不抓取套餐内容**。套餐与协议仍需人工核验，写在 `verified` 里。

## scripts/validate-links.mjs 校验了什么

1. **结构**：顶层字段类型、`links` 非空、每条记录必填字段齐全；
2. **枚举**：`category` / `urlKind` 取值合法；
3. **唯一性**：`id` 与 `url` 不重复；
4. **链接形式自洽**：
   - `hash-deep-link` 的 fragment 必须以 `#@command:` 开头、命令名合法、参数里含 `code`、推广码与 `referralCode` 一致、且 query 中不得同时出现 `code`；
   - `path-referral` 不得带 fragment，query 的 `code`/`cover` 必须与字段一致；
   - `path-page` / `plain` 不得携带 `code`/`cover`；
5. **交叉约束**：`affiliate` 类不得有推广码；`punycodeDomain` 与 `unicodeDomain` 不得相同；
6. **内容下限**：`purpose` 非空且不过短、`description` 与 `tags` 非空、各数组字段类型正确；
7. **核验记录**：日期格式、状态码范围、方法与结论非空；403 条目必须说明被风控拦截；
8. **巡检记录**（若存在 `probe`）：health 取值合法、状态码与 health 自洽（`cloudflare` 只允许配 403/429/503）、`probe.backups` 条目数必须等于 `backupUrls` 且地址必须是已声明的备用入口、致命状态的 detail 必须说明原因。

退出码：`0` 通过，`1` 有错误。

## scripts/render-readme.mjs

- 读取 `data/links.json`，渲染两块：`LINKS_TABLE`（速览表格）与 `LINKS_DETAILS`（逐条说明）。
- 用成对标记注释替换 README 中的对应区块，区块外的文字**原样保留**。
- `--check` 模式不写文件，只比对；有差异则退出码 1，供 CI 使用。

## 零依赖的理由

三个脚本只使用 Node 内置模块（`node:fs` / `node:url` / `node:path`），仓库里**没有 `package.json`、没有 `node_modules`、没有锁文件**。收益：

- `git clone` 之后不需要任何安装步骤就能跑校验；
- 没有供应链攻击面；
- CI 的环境准备只有一行 `actions/checkout`。

代价是无法用第三方 schema 校验器（如 ajv）。**当前 schema 由人工维护，校验逻辑写死在脚本里**；若将来需要完整的 schema 校验，再引入 ajv，届时加 `package.json` 也不迟。

## 扩展方向

- **新增链接形式**：先在 `docs/link-formats.md` 定义语义，再在 `links.schema.json` 的 `urlKind` 枚举与校验器里加分支，最后改渲染器。
- **新增字段**：`data/links.json` 加字段 → schema 加定义 → 校验器加规则 → 渲染器决定是否输出。
- **接入自动可达性巡检**：新增 `scripts/check-links.mjs`，定期请求各条目并把结果写回 `verified`。**注意**：多数站点有 Cloudflare，必须区分 200 与 403，且不要把 403 当作失效。
