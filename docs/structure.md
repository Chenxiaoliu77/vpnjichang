# 目录结构与文件组织

本文面向**仓库维护者**，说明 vpnjichang 的目录为什么这么切、每个文件负责什么、扩展时该往哪里加。

## 全貌

@@BT@@
vpnjichang/
├── README.md                  # 项目说明 + 收录清单（清单区块由脚本渲染生成）
├── CHANGELOG.md               # 变更记录：每次增删改收录项都记一笔
├── CONTRIBUTING.md            # 贡献指南：如何新增 / 更新 / 下架一个收录项
├── LICENSE                    # MIT 许可证
├── .gitignore                 # 忽略 Node 依赖与本地临时文件
├── .github/
│   └── workflows/
│       └── ci.yml             # CI：结构校验 + README 渲染一致性检查
├── data/
│   ├── links.json             # ★ 收录清单唯一真源（结构化数据）
│   └── links.schema.json      # links.json 的 JSON Schema
├── docs/
│   ├── structure.md           # 本文件
│   └── link-formats.md        # 链接形式规范：深链 / 服务端推广码 / 渠道标记
└── scripts/
    ├── validate-links.mjs     # 零依赖校验器：结构、参数一致性、重复项
    └── render-readme.mjs      # 由 links.json 渲染 README 的清单区块
@@BT@@

## 核心设计：单一真源 + 渲染

### 数据流

@@BT@@
data/links.json  ──┬──>  scripts/validate-links.mjs  ──>  结构/一致性校验（CI 步骤 1）
                    │
                    └──>  scripts/render-readme.mjs  ──>  README.md 的清单区块（CI 步骤 2 校验一致性）
@@BT@@

**唯一真源是 @@BT@@data/links.json@@BT@@。** README 里由脚本托管的两块内容被成对的标记注释包住：

@@BT@@
<!-- BEGIN:LINKS_TABLE (generated by scripts/render-readme.mjs; do not edit by hand) -->
<!-- END:LINKS_TABLE -->

<!-- BEGIN:LINKS_DETAILS (generated by scripts/render-readme.mjs; do not edit by hand) -->
<!-- END:LINKS_DETAILS -->
@@BT@@

在这两块里手写内容会在下次渲染时被**静默覆盖**。CI 用 @@BT@@node scripts/render-readme.mjs --check@@BT@@ 兜底：只要 README 与数据不一致，CI 立刻失败，不会让覆盖悄悄发生。

### 为什么不用 Markdown 当真源

如果清单直接写在 Markdown 里，就会出现两难：Markdown 好读但机器不好解析；JSON 好解析但人不好维护。折中方案是**JSON 存数据 + 脚本渲染 Markdown**，代价是多一个渲染步骤，收益是：

- 清单能被程序校验（重复 URL、推广码与链接形式不匹配、id 冲突……）；
- 字段的必填与类型由 schema 约束，新增条目不会漏字段；
- 改一次数据，README 的表格和正文同步更新，不会出现「表格里改了、正文里忘了改」。

### 标识类

- **@@BT@@id@@BT@@** —— 条目唯一标识，小写字母/数字/连字符。它是变更追踪的锚点，**一旦发布就当作破坏性变更**：改名等于换一个条目。
- **@@BT@@name@@BT@@ / @@BT@@nameZh@@BT@@** —— 对外展示名。@@BT@@nameZh@@BT@@ 可以带上站点的自述标语（如「良心云 最良心的高性价比机场」），便于识别。

### 域名类

- **@@BT@@punycodeDomain@@BT@@ / @@BT@@unicodeDomain@@BT@@** —— IDN 域名的两种写法。校验器强制两者不得相同（即不得有一方被写成另一方的复制），确保是真的做了 Punycode ↔ Unicode 对照，而不是把同一个字符串填两遍。

### 分类类

- **@@BT@@category@@BT@@** —— 机器可读枚举，取值：
  - @@BT@@provider@@BT@@ —— 机场/代理订阅服务商；
  - @@BT@@affiliate@@BT@@ —— 联盟推广后台（如 mitce 的 @@BT@@affiliates.php@@BT@@）；
  - @@BT@@mirror@@BT@@ —— 镜像/备用入口；
  - @@BT@@tool@@BT@@ —— 工具类；
  - @@BT@@tutorial@@BT@@ —— 教程。
- **@@BT@@categoryLabel@@BT@@** —— 人类可读的中文标签，直接渲染进表格。

### 链接类

- **@@BT@@url@@BT@@** —— 完整地址，必须是 @@BT@@https://@@BT@@。
- **@@BT@@urlKind@@BT@@** —— 决定推广码该放在哪里，也是校验器判断一致性的依据：

  | 取值 | 含义 | 推广码位置 |
  | --- | --- | --- |
  | @@BT@@hash-deep-link@@BT@@ | 客户端深链 | fragment：@@BT@@#@command:<cmd>?code=...@@BT@@ |
  | @@BT@@path-referral@@BT@@ | 服务端推广链接 | query：@@BT@@?code=...&cover=...@@BT@@ |
  | @@BT@@path-page@@BT@@ | 站内页面 | 无 |
  | @@BT@@plain@@BT@@ | 普通链接 | 无 |

- **@@BT@@referralCode@@BT@@** —— 推广码。校验器强制：@@BT@@hash-deep-link@@BT@@ 与 @@BT@@path-referral@@BT@@ 必须有，@@BT@@affiliate@@BT@@ 类必须没有。
- **@@BT@@cover@@BT@@** —— 渠道/落地页来源标记，**只允许出现在 @@BT@@path-referral@@BT@@ 里**。

### 内容类

- **@@BT@@purpose@@BT@@** —— 一句话，回答「这条地址是干什么的」。
- **@@BT@@description@@BT@@** —— 分段说明数组。写清三件事：**站点性质**（是服务商还是联盟页）、**链接参数含义**、**注意事项**（如需浏览器打开、需登录）。
- **@@BT@@tags@@BT@@** —— 短标签，用于表格速览与检索。
- **Q}pricing@@BT@@ —— 站点**公开公示**的套餐。只填页面上真实看到的，不填推测值。
- **Q}platforms@@BT@@ / @@BT@@protocols@@BT@@** —— 支持平台；客户端与协议标识。
- **Q}backupUrls@@BT@@ / @@BT@@contact@@BT@@** —— 备用入口（防失联发布页、备用域名）与客服/社群。

### 核验类

- **@@BT@@verified.checkedAt@@BT@@** —— 核验日期（@@BT@@YYYY-MM-DD@@BT@@）。
- **Q}verified.httpStatus@@BT@@** —— 实测 HTTP 状态码。**403 是合法且常见的结果**，表示站点部署了 Cloudflare 人机校验。
- **Q}verified.finalUrl@@BT@@** —— 跟随重定向后的最终地址。
- **Q}verified.method@@BT@@** —— 核验方式，如 @@BT@@curl + read_page@@BT@@。
- **Q}verified.note@@BT@@** —— 核验结论与**未核验事项**。这一条最要紧：写清「哪些信息没验证到」，避免读者把空白误读成「该特性不存在」。

## scripts/validate-links.mjs 校验了什么

1. **结构**：顶层字段类型、@@BT@@links@@BT@@ 非空、每条记录必填字段齐全；
2. **枚举**：@@BT@@category@@BT@@ / @@BT@@urlKind@@BT@@ 取值合法；
3. **唯一性**：@@BT@@id@@BT@@ 与 @@BT@@url@@BT@@ 不重复；
4. **链接形式自洽**：
   - @@BT@@hash-deep-link@@BT@@ 的 fragment 必须以 @@BT@@#@command:@@BT@@ 开头、命令名合法、参数里含 @@BT@@code@@BT@@、推广码与 @@BT@@referralCode@@BT@@ 一致、且 query 中不得同时出现 @@BT@@code@@BT@@；
   - @@BT@@path-referral@@BT@@ 不得带 fragment，query 的 @@BT@@code@@BT@@/@@BT@@cover@@BT@@ 必须与字段一致；
   - @@BT@@path-page@@BT@@ / @@BT@@plain@@BT@@ 不得携带 @@BT@@code@@BT@@/@@BT@@cover@@BT@@；
5. **交叉约束**：@@BT@@affiliate@@BT@@ 类不得有推广码；@@BT@@punycodeDomain@@BT@@ 与 @@BT@@unicodeDomain@@BT@@ 不得相同；
6. **内容下限**：@@BT@@purpose@@BT@@ 非空且不过短、@@BT@@description@@BT@@ 与 @@BT@@tags@@BT@@ 非空、各数组字段类型正确；
7. **核验记录**：日期格式、状态码范围、方法与结论非空；403 条目必须说明被风控拦截。

退出码：@@BT@@0@@BT@@ 通过，@@BT@@1@@BT@@ 有错误。

## scripts/render-readme.mjs

- 读取 @@BT@@data/links.json@@BT@@，渲染两块：@@BT@@LINKS_TABLE@@BT@@（速览表格）与 @@BT@@LINKS_DETAILS@@BT@@（逐条说明）。
- 用成对标记注释替换 README 中的对应区块，区块外的文字**原样保留**。
- @@BT@@--check@@BT@@ 模式不写文件，只比对；有差异则退出码 1，供 CI 使用。

## 零依赖的理由

两个脚本只使用 Node 内置模块（@@BT@@node:fs@@BT@@ / @@BT@@node:url@@BT@@ / @@BT@@node:path@@BT@@），仓库里**没有 @@BT@@package.json@@BT@@、没有 @@BT@@node_modules@@BT@@、没有锁文件**。收益：

- @@BT@@git clone@@BT@@ 之后不需要任何安装步骤就能跑校验；
- 没有供应链攻击面；
- CI 的环境准备只有一行 @@BT@@actions/checkout@@BT@@。

代价是无法用第三方 schema 校验器（如 ajv）。**当前 schema 由人工维护，校验逻辑写死在脚本里**；若将来需要完整的 schema 校验，再引入 ajv，届时加 @@BT@@package.json@@BT@@ 也不迟。

## 扩展方向

- **新增链接形式**：先在 @@BT@@docs/link-formats.md@@BT@@ 定义语义，再在 @@BT@@links.schema.json@@BT@@ 的 @@BT@@urlKind@@BT@@ 枚举与校验器里加分支，最后改渲染器。
- **新增字段**：@@BT@@data/links.json@@BT@@ 加字段 → schema 加定义 → 校验器加规则 → 渲染器决定是否输出。
- **接入自动可达性巡检**：新增 @@BT@@scripts/check-links.mjs@@BT@@，定期请求各条目并把结果写回 @@BT@@verified@@BT@@。**注意**：多数站点有 Cloudflare，必须区分 200 与 403，且不要把 403 当作失效。
