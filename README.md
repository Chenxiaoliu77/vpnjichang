## 这个仓库是什么

机场（也叫「机场」/ 机场订阅）是提供代理节点订阅的商业服务：付费购买流量套餐后，得到一条**订阅链接**，导入 Clash、Shadowrocket、Surge、sing-box 等客户端即可使用。

但这类服务有几个现实问题：

- **域名频繁更换**——被墙、被封、换域名，老链接经常打不开；
- **信息不透明**——价格、流量、协议、客户端支持情况往往要登录才能看到；
- **推广链接参数混乱**——同一个推广码可能出现在 hash 片段里，也可能出现在 query 里，二者的统计行为完全不同。

本仓库做三件事：

1. **收录**：维护一份结构化的推广/入口地址清单；
2. **说明**：逐条解释每个地址的用途、参数含义、站点性质与实测核验结果；
3. **保鲜**：用脚本做结构校验与文档一致性检查，让清单与文档不会互相漂移。

**本仓库不提供任何节点、账号、配置或订阅内容**，只收录公开的推广入口与说明信息。

## 链接形式说明：为什么有的带 `#@command:...`、有的带 `?code=...`

这是本仓库最需要讲清楚的一点，直接影响**推广码能不能被统计到**。

### 1. 客户端深链（hash 片段）

形如：

`https://example.com/#@command:register?code=o31fm0TO`

- **`#@command:register`** 是命令前缀，常见取值：
  - `register` —— 打开即进入注册流程；
  - `quick` —— 打开即进入快速下单流程；
  - `login` / `subscribe` 等其他命令。
- **`code=o31fm0TO`** 是推广/邀请码。

**关键点**：`#` 后面的内容是 URL 的 **fragment（片段）**。按 HTTP 规范（RFC 3986 §3.5）fragment **不会随请求发送给服务器**，服务器只会收到 `https://example.com/`。推广码是由客户端或页面脚本在浏览器端读取并带入注册表单的。

**影响**：
- 优点：跳转干净、不污染服务器日志，适合做「一键注册」体验；
- 缺点：**依赖前端 JS 正确解析**。若目标站点前端逻辑变更、或链接被放进不支持该约定的客户端，推广码会静默丢失——注册能成功，但**不会产生佣金归因**。

### 2. 服务端推广链接（query 参数）

形如：

`https://example.com/register?code=ipPmzlHT&cover=sfw`

- **`code=ipPmzlHT`** —— 推广/邀请码，**服务器能直接收到**；
- **`cover=sfw`** —— 渠道/落地页来源标记，用于按推广位拆分转化与结算。

**影响**：
- 优点：**归因稳定**。即使前端有 bug，服务器仍然记录了邀请关系；
- 缺点：URL 略长，且参数会出现在服务器访问日志、Referer 头和浏览器历史里。

### 3. 站内页面（无推广参数）

形如：

`https://mitce.io/affiliates.php`

服务器端页面，通常**需要登录**才能看到核心内容（如联盟推广链接、佣金结算面板）。

### 一句话对比

| 形式 | 推广码位置 | 服务器可见 | 归因可靠性 | 典型用途 |
| --- | --- | --- | --- | --- |
| 客户端深链 | `#@command:xxx?code=...` | 不可见 | 依赖前端解析，弱 | 一键注册 / 一键下单体验 |
| 服务端推广链接 | `?code=...&cover=...` | 可见 | 服务端记录，强 | 渠道归因与佣金结算 |
| 站内页面 | 无 | — | 不适用 | 联盟后台、教程、状态页 |

**收录建议**：需要可靠归因时优先用**服务端推广链接**；追求「点开即注册」体验时用**客户端深链**，但要知道它的归因是尽力而为的。

### Punycode 域名说明

清单里多个机场使用 Punycode 域名（`xn--9kqs1lo79d.com` 这类）。这是国际域名标准（IDN）的 ASCII 兼容编码，浏览器地址栏通常会自动显示成 Unicode 形式：

| Punycode | Unicode |
| --- | --- |
| `xn--9kqs1lo79d.com` | 吹雪云.com |
| `xn--mes358aby2apfg.com` | 赔钱机场.com |
| `xn--4gqx1hgtfdmt.com` | 一分机场.com |
| `xn--9kqz23b19z.com` | 良心云.com |

## 仓库目录结构与文件组织

```text
vpnjichang/
├── README.md                  # 项目说明 + 收录清单（清单区块由脚本渲染生成）
├── CHANGELOG.md               # 变更记录：每次增删改收录项都记一笔
├── CONTRIBUTING.md            # 贡献指南：如何新增 / 更新 / 下架一个收录项
├── LICENSE                    # MIT 许可证
├── .gitignore                 # 忽略 Node 依赖与本地临时文件
├── .github/
│   └── workflows/
│       └── ci.yml             # CI：结构校验 + README 渲染一致性检查
├── data/
│   ├── links.json             # ★ 收录清单唯一真源（结构化数据）
│   └── links.schema.json      # links.json 的 JSON Schema
├── docs/
│   ├── structure.md           # 目录结构与文件组织方式的详细说明
│   └── link-formats.md        # 链接形式规范：深链 / 服务端推广码 / 渠道标记
└── scripts/
    ├── validate-links.mjs     # 零依赖校验器：结构、参数一致性、重复项
    └── render-readme.mjs      # 由 links.json 渲染 README 的清单区块
```

### 为什么这样组织

**1. 数据与文档分离，文档由数据渲染**

`data/links.json` 是唯一真源。README 里的清单表格与逐条说明由 `scripts/render-readme.mjs` 生成，两处内容被标记注释包住：

```text
<!-- BEGIN:LINKS_TABLE (generated by scripts/render-readme.mjs; do not edit by hand) -->
...
<!-- END:LINKS_TABLE -->
```

好处：改数据时只需改一处，文档不会漂移；CI 用 `--check` 校验两者一致，避免手改被覆盖后没人发现。

**2. 每个收录项是一份可校验的结构化记录**

`links.json` 中每条记录都带固定字段：分类、链接形式、推广码、渠道标记、用途、详细说明、标签、公示套餐、支持平台、客户端/协议标识、备用入口、客服，以及**核验记录**（核验日期、HTTP 状态、最终 URL、核验方式与结论）。

**核验记录是刻意设计的**：机场站点普遍部署 Cloudflare 人机校验，脚本直连会拿到 403。清单里因此同时存在「HTTP 200 可直连」和「HTTP 403 被风控拦截、需浏览器打开」两种状态——如实标注可达性，比给出一个笼统的「可用」更诚实。

**3. 脚本零依赖**

只用 Node 内置模块（`node:fs` / `node:url` / `node:path`），没有 `package.json`、没有 `node_modules`、没有第三方依赖。克隆下来就能跑：

```bash
node scripts/validate-links.mjs        # 校验清单结构
node scripts/render-readme.mjs         # 重新渲染 README 清单区块
node scripts/render-readme.mjs --check # 只校验一致性（CI 用）
```

**4. 文档分层**

`README.md` 面向访客（这是什么、清单在哪、每条地址干什么）；`docs/structure.md` 面向维护者（目录为什么这么切、字段含义、扩展方式）；`docs/link-formats.md` 面向要收录新地址的人（链接形式怎么选、参数怎么填）。

### 字段速查

| 字段 | 含义 |
| --- | --- |
| `id` | 唯一标识，小写字母/数字/连字符，变更时视为破坏性改动 |
| `category` | `provider`（服务商）/ `affiliate`（联盟推广）/ `mirror`（镜像）/ `tool`（工具）/ `tutorial`（教程） |
| `urlKind` | `hash-deep-link` / `path-referral` / `path-page` / `plain`，决定推广码该放哪 |
| `referralCode` | 推广码，位置必须与 `urlKind` 一致 |
| `cover` | 渠道/落地页来源标记，只出现在服务端推广链接里 |
| `description` | 逐条说明数组，讲清站点性质、链接参数含义与注意事项 |
| `verified` | 核验记录：日期、HTTP 状态、最终 URL、核验方式与结论 |

完整字段定义见 [`data/links.schema.json`](data/links.schema.json) 与 [`docs/structure.md`](docs/structure.md)。

## 如何新增一条收录

1. 克隆仓库并新建分支；
2. 在 `data/links.json` 的 `links` 数组里追加一条记录，按 [schema](data/links.schema.json) 填全字段；
3. 运行 `node scripts/validate-links.mjs` 通过校验；
4. 运行 `node scripts/render-readme.mjs` 重新生成 README 清单区块；
5. 提交 PR，CI 会自动校验结构与渲染一致性。

详细步骤与字段填写注意事项见 [CONTRIBUTING.md](CONTRIBUTING.md)。

## 核验方法与诚实声明

本清单的每条记录都经过实测核验，核验方式如实记录在 `verified.method` 中：

- **curl + read_page** —— 用脚本请求并抓取渲染后的页面内容，提取站点自述的产品名、套餐价目、客户端支持与协议标识；
- **HTTP 403 的条目** —— 站点部署 Cloudflare 人机校验，脚本直连会被拦截（返回 `Just a moment...`），这类条目标注为「需在浏览器中打开」，**其套餐与协议信息未经登录态核验，清单中不做推测性描述**。

清单中标注「未核验」的字段表示**当时没有验证到**，不代表内容不存在——请以站点实际页面为准。
